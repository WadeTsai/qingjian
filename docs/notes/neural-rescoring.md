# 字級 Transformer 重打分：評測（2026-09-08）

## 做了什麼

- 模型：兩檔字級 decoder，small 23M、base 36M / 上下文 256，語料為中文維基 + LCCC（訓練細節不在本倉庫）。
- 推理：`crates/qingjian-neural`（candle），與訓練指令碼的 Python 打分對拍一致。M1 上 Metal 後端最快：空前文單條 6 ms，
  64 字前文 × 8 條 133 ms；CPU（Accelerate）約慢一倍，candle 自帶 gemm 再慢一倍。按 token 算吞吐很低，是每層十幾個小運算元的排程開銷在主導。
- 接法：Core `sentence::convert_paths` 出 Viterbi 前 6 條路徑，`Engine` 按 `路徑分 + λ·(神經分 − 靜態二元分)` 重排，
  神經分只替換靜態二元的判斷，個人 n-gram、使用者加分、敲錯代價原樣保留（早先試過 `(1 − λ)·路徑分 + λ·神經分` 的線性混分，
  λ 0.5 時個人計數被稀釋得厲害）。前文是本會話最近上屏的 64 個字元。只有 CLI `--neural` 接它。

## 明細說明回放這把尺子在整句上量不準

最好的一檔（靜態 λ 0.25 前文 64）逐條對賬：變差 43 條、變好 45 條。變差裡一大批是**模型對、日誌錯**：
`shurukuang` 日誌選了 輸入狂、模型給 輸入框；`tiaoshi` 條是 → 除錯；`gengkuai` 更會 → 更快；`jiaohu` 叫和 → 互動；
`siyou` 死有 → 私有；`zuoyong` 做用 → 作用；`hade` 哈的 → 好的。日誌裡「選了」的整句多半是當時按空格接受的基線自己的輸出，
誤選也照記，所以基線在整句上天然佔便宜。真正模型錯的：我的 → 沃德 ×4（雲端學來的錯讀音使用者詞），資料 → 字了，才對 → 猜對。
變好的是 候選框 ×4、我之前 ×2、實際 ×2、不顯示 ×2、增量、實現、下載、本地、目錄、資源庫、重寫、進度 這類實詞。

- **過了門檻**：最好一檔比基線高 4.3 個點，字準確率高 2.2 個點；連最便宜的一檔（λ 0.5 不給前文，21 ms）也有 +2.2。

- 絕對數字低（基線 37.6%）是文本的性質：技術筆記與本倉庫的設計文件，行話密（候選 / 詞庫 / 釋義表 / 敲錯），
  `docs/` 那部分基線只有 27.8%，個人筆記 46.5%。這個集是冷啟動、沒有個人 n-gram；實際使用裡個人計數會補掉一部分同樣的錯，
  模型的淨增益會比這裡小一些。

翻壞的多半是切句後失去了上下文的短句裡的虛詞 / 單字同音（是 / 時 / 先、會 / 回、見 / 建、拿 / 那、該 / 改），
還有 全綠 → 全旅 ×3、服務商 → 服務上 ×2、技術面試 → 及書面是 這類模型沒見過的搭配。

## 進殼（2026-09-08 晚）

1. **前文 KV 快取**（`qingjian-neural::PrefixCache`）：前文在一次組句裡不變，每層的 K / V 算一次存下來；每條候選只算「前文最後一個 token + 候選」這一小段，
   前文快取部分不含最後一個 token，它的輸出分佈正好給候選第一個字用。Metal 上 64 字前文 × 8 條 133 → 28 ms，空前文 8 條 20 ms；
   剩下的是每層十幾個小運算元的排程開銷，CPU（candle gemm）同樣的活要 73 ms，還是 Metal。與 Python 對拍不變。
2. **Core 非同步重排**（`engine/rescoring/`）：一次查詢裡整句轉換會跑好幾遍（糾錯變體、中英混輸比分），所有路徑文本進一張「前文 + 文本 → 神經分」快取；
   同步打分器當場補分（評測每句 69 → 27 ms），非同步的先記下缺分的文本，殼停鍵後 `request_rescoring` 一次送後臺執行緒（幾條攢一批），
   `poll_rescoring` 收到後再 `query` 一次就全在快取裡。CLI `--neural-async` 走同一條路，300 句上與同步結果逐句一致。
3. **殼**：知微模型隨包放 `Resources/models/hanzhang-zhiwei/`（56 MB fp16），後臺執行緒載入 + 預熱後接上；每鍵先讀應用游標前 64 字當前文（應用給不出退回本會話歷史），
   停鍵 80 ms 請求、20 ms 輪詢，結果到了只重畫當前頁，翻過頁或動過高亮不打擾。`[model] enabled` 開關在「雲服務」頁。
   TextEdit 端到端：`houxuanshengcheng` 候選聲稱 → 候選生成，`shururizhi` 輸入日至 → 輸入日誌。

## 結論與下一步

模型有資訊、接法成立，**在不帶日誌偏差的尺子上過了「整句 +2 個點」的門檻**（+4.3）。回放上看到的「整句變差」是尺子的問題。下一步按順序：

1. 延遲已解決到能進殼（上一節）；再往下是運算元合併或量化，以及模型後臺載入的 12 秒（首次 Metal 編譯）。
2. 應用上下文已接：IMK 的 surrounding text 當前文，評測集裡的「上文」就是它的模擬。
3. 資料：語料裡沒有技術文本，`輸入框`、`候選框`、`全綠`、`服務商` 這類詞靠個人微調補；閒時訓練那一步才是「越用越像自己」的來源。
4. λ 預設已從 0.25 提到 0.5（0.75 最高但與 0.5 只差 0.3 個點，留點餘量給個人 n-gram）。
5. 發版：資料包要帶模型，權重許可另定。

## 2026-09-24 換 P2C 之後：兩個 bug、一個架構上限

整句重排從含章·知微（字級模型）換成含章·通變（P2C，`crates/qingjian-neural::P2cScorer`）之後在凍結集上是 42.5% / 字準 79.3%，
但日常打字裡中英混輸整個壞掉：`woxiangxuexirust` 出 我想學習如斯。下面三件事是一次查出來的。

### 一、神經分不能寫回 `Conversion::score`

P2C 打的是 `log P(漢字 | 拼音)`，字級模型打的是 `log P(漢字)`。前者被拼音條件住，比靜態二元分高十幾二十 nat，
抬升還隨句子長短與靜態模型的偏好變化，**不是常數偏移**。原來的 `rescore_paths` 把 `路徑分 + λ·(神經分 − 靜態分)` 寫回 `score`，
這個被抬高的分就漏進了兩處跨讀法的比較：

- `find_correction`：原樣能轉出的整句分 vs 糾正後的整句分。
- `mixed_beats_plain`：混輸頭段分 + 英文詞機率 vs 整段按拼音讀的分。

兩處的門檻（`correction_cost`、`ENGLISH_SWITCH_PENALTY`）都是按靜態尺度定的。實測 `woxiangxuexirust`：

| | 原樣 | 糾正後 | 結果 |
| --- | --- | --- | --- |
| 無模型 | −33.83 | −36.18 | 不糾 |
| 字級 LM λ0.75 | −33.58 | −36.48 | 不糾 |
| P2C λ0.75 | −16.90 | −13.87 | 糾成 我想學習如斯 |

更根本的原因：按貝葉斯 `log P(漢字|拼音) = log P(拼音|漢字) + log P(漢字) − log P(拼音)`，
最後那項只在**同一串按鍵**下是常數，而這兩處比較的兩邊按鍵本來就不同。所以 P2C 的分只在同一串按鍵內可比。

改法：`rescore_paths` 只排名次，`score` 原樣不動。凍結集不變（42.5% / 79.3%），混輸恢復。

### 二、長句只給一條整句候選太少

`convert_sentence_with` 內部已經算了 `RESCORE_PATHS` 條並重排好，卻只取第一條。凍結集 2081 句（全集每 4 句取 1）上：

| | 首選 | 前三 | 前五 |
| --- | --- | --- | --- |
| 改前 | 42.3% | 42.4% | 42.4% |
| 改後（`SENTENCE_CANDIDATES = 3`） | 42.3% | **45.5%** | 45.5% |
| 試過 5 條 | 42.3% | 45.5% | 45.7% |
| 無模型、改後 | 38.0% | **43.2%** | 43.2% |

給 5 條只再多 0.2 個點卻擠掉整頁詞級候選，定 3 條；四個音節以下不給備選（那幾格留給詞級候選更值）。
無模型時也漲說明這不依賴神經模型，`sentence_paths` 的 `want` 引數讓拼寫糾錯那條路仍然只算一條（它對每個糾正候選都要轉一次）。

**坑**：第一版把「第一條不合格就繼續找下一條」寫成了 `continue`，結果 `nihao` 的最優路徑 你好 是單個詞（不算句子）被跳過，
第二條 你號 頂上來插到詞庫詞 你好 前面。第一條不合格必須整條不出。

### 三、重排這層架構本身是瓶頸

同一份 2081 句，P2C **自由生成**（`P2c::convert`，束寬 5，不經詞圖不經重排）對比產品的重排路徑：

| | 首選 | 前三 / 前五 | 字準 |
| --- | --- | --- | --- |
| 詞圖 + P2C 重排 | 42.3% | 45.5% | 78.5% |
| P2C 自由生成 | **51.9%** | 前五 **73.5%** | **83.0%** |

逐句配對：兩邊都對 35.4%，**只有生成對 16.5%，只有重排對 6.9%**，都不對 41.1%（McNemar χ²=81.1）。
兩條路是互補的，不是替代關係——重排那 6.9% 來自詞庫、個人學習、輔碼、混輸，生成給不了。

並起來能到哪：

- 首選並集上限 58.9%
- 重排前三 ∪ 生成前二（佔 5 格）**68.2%**
- 重排前三 ∪ 生成前五（佔 8 格）75.9%

評測集是本專案自己的中文文件抽的，與 P2C 的訓練語料（wikipedia / LCCC / IndustryCorpus2）不重疊，不是記憶效應。

代價是延遲：生成是 `O(生成字數)` 次序列前向（同一份集合上平均 130～200 ms、最慢 2.4 s），
重排是一次批次前向（平均 62 ms）。這是結構差異不是調參旋鈕，要進產品得先解決。

實驗入口：`--eval-text <集> --eval-generate data/models/hanzhang-tongbian/hanzhang-tongbian-small.qjm [--eval-details out.jsonl]`。
