# 模型假設與驗證尺子

輸入法裡「模型可能能做的事」不止整句重排一件。每一件在動手之前都要先回答：用什麼指標算成功、指標從哪些資料算、
現在的基線是多少。基線算不出來的假設不立項。這份檔案記每個假設的尺子；輸入日誌（`input-log.jsonl`）按這裡的需要定格式，
回放評測（`qingjian-cli --replay`）按這裡的指標出報告。

## 原則

- 日誌記的是**情境、給的、做的、事後反饋**四件事，不是某個模型的特徵。欄位與模型無關，任何排序 / 預測 / 糾正類假設都能回放驗證。
- 漏記的補不回來，多記的代價很低：情境資料只要隱私成本接近零就記。
- **不記**應用裡的游標前文（含使用者沒通過青簡打的內容）、逐鍵時間戳、Secure Input 期間的任何東西。
- 每個假設先寫指標與基線，再改程式碼；改完在**同一份凍結日誌**上比（日誌是活的，兩次複製的不一樣）。
- 日誌驗不了的（延遲、UI 感受、反事實「當時給了 X 會不會選」）只能自己用；反事實只在 X 恰好出現在使用者最終文本時近似。

## 日誌格式 v1

一行一條 JSON，`t` 是本機時間戳，`event` 是事件名；讀端跳過不認識的事件與欄位，以後加欄位不升版本。

| 事件 | 何時 | 欄位 |
|---|---|---|
| `session` | 輸入法啟動、日誌開關開啟時 | `v` 格式版本、`version` 輸入法版本、`platform`、`model` 本地整句模型開沒開、`scheme` 雙拼方案 |
| `commit` | 每次上屏 | 原有：`id` `scope` `keys` `pinyin` `corrected` `text` `source` `index` `top`（一頁 9 條）`scheme` `english`；新增：`rescored` 候選順序經過神經重排、`app` 應用標識、`pages` 翻了幾頁、`ms` 首鍵到上屏的毫秒 |
| `retract` | 上屏後整個退格刪掉、同段拼音改選了別的 | `of` `text` `chosen` |
| `retype` | 組句裡退格重打，最終鍵串與第一次退格前不同；或上屏後刪掉重打了不同的鍵 | `before` `after` `of`（對應的上屏 `id`） |
| `passthrough` | 組句外直打的標點 / 回車 / 空格，攢到下一次上屏或邊界時寫 | `text` |
| `prediction` | 雲端聯想結果到達並展示 | `scope` `words` `sentence` |
| `break` | 上文鏈斷開（切應用、失焦、清空） | `app` 新應用標識 |

## 假設與尺子

| 假設 | 指標 | 用哪些欄位 | 基線 |
|---|---|---|---|
| 整句重排（已做） | 詞 / 整句首選命中 | `commit` 的 `top` `index` | 2026-09-12 凍結日誌 12886 條可評：詞 86.9% / 整句 90.2% / 英文 82.9%（原樣上屏也回放進學習之後；之前的 72.5% 是回放沒學個人英文詞）；短語層進詞庫後 87.3% / 88.2% / 82.5%（整句掉的多半是舊引擎沒有短語時使用者只能選字首的偏差，見 `docs/notes/phrase-layer.md`）；領域詞 48 條進詞庫後 87.6% / 88.4% / 82.5%（`docs/notes/domain-words.md`） |
| 排序常數（個人 n-gram 插值 λ / K / 封頂 / D，敲錯四類代價 / 折扣上限 / 整段糾錯代價） | 同上，`--tune 名=值` 掃網格 | 同上 | 2026-09-12 掃過一輪：全在平臺區，見 `docs/notes/constant-sweep.md` |
| 個人微調（LoRA） | 按天留出的首選命中 | `commit` 文本流 + `passthrough` + `break` | 同上，待按天切 |
| 敲錯糾正 | 對 `retype` 的召回、對正常輸入的誤糾率 | `retype`、`commit.corrected` | 待攢（事件新加） |
| 本地聯想替代雲端 | 預測的下一詞 = 使用者接著打的詞；雲端被接受的比例 | `prediction` + 緊接的 `commit.source` | 待攢 |
| 中英混輸判定 | 判成英文 vs 使用者原樣上屏 | `commit.source == raw` 且鍵像英文詞 | 可從現有日誌算 |
| 候選質量的隱式訊號 | 翻頁數、組句耗時與命中率的相關性 | `commit.pages` `commit.ms` | 待攢 |
| 按應用風格 | 分應用的首選命中 | `commit.app` | 待攢 |
| 長句切分 / 簡拼展開 | 切分與最終文本的對齊 | `commit.pinyin` `commit.text` | 可從現有日誌算 |
| 神經重排的淨效果 | `rescored` 為真 / 假兩組的首選命中 | `commit.rescored` | 待攢 |
| 神經 P2C（帶噪拼音直接生成漢字） | 整句首選 + 一次重解碼的耗時，兩者都要過 | `commit` 的 `keys` `pinyin` `corrected` `text`（天然就是「帶噪拼音 → 正確文本」的監督對） | 整句首選 41.6%（凍結集 8322 句，當前帶重排的成績，**不是裸基線 37.6%**）；延遲見下節與 `docs/notes/p2c-latency-spike.md` |

## 神經 P2C 的延遲門檻（2026-09-20 量過）

這個假設與別的不同：**準確率贏了但延遲不達標，一樣不立項**。把詞庫召回換成模型生成之後，
候選的存在本身就依賴模型，而拼音字首每敲一鍵就變、整句要重解碼一次，所以延遲是第一道門檻而不是最後一道。

`crates/qingjian-neural/examples/p2c_bench.rs` 在 M1 本機拿現有字級模型當代理量過一輪（完整表格與偏差說明見
`docs/notes/p2c-latency-spike.md`）。**延遲只能在目標裝置上量，租的卡量不了**：使用者跑的是 mac 的 Metal 與 Windows 的 CPU。

| 項 | 門檻 | 代理模型（full-small 23M） |
|---|---|---|
| 一次整句重解碼（Metal，前文 64，beam 4，8 字） | < 100 ms | 68 ms ✔ |
| 同上，CPU | < 150 ms | 141 ms（勉強）|
| 每鍵增量（前文 64 字，推進 1 個 token） | < 10 ms | Metal 2.1 / CPU 6.7 ✔ |
| 模型載入 | < 500 ms | 66 ms ✔ |

已知結論：拼音字首可快取、成本可忽略；瓶頸是解碼的前向（佔 Metal 66% / CPU 95%），把 top-k 搬上 GPU 也只省掉
Metal 那 28%。因此 P2C 當同步主候選不成立（beam 8 / 16 字 Metal 218 ms、CPU 416 ms，追不上 5 到 8 鍵每秒的手速），
可行的位置是現有的停鍵非同步槽位，詞庫繼續出同步候選。

P2C 值得試的理由是它能做三件當前架構做不到的事：未登入詞按字生成、糾錯進模型本身、
**句中英文**（現在 `english_tail.rs` 只支援句末尾段，見「中英混輸判定」那一行）。三件在離線前提下都沒有別的解法。

## 已知的尺子偏差

- 日誌裡「選了」的整句多半是當時按空格接受的基線自己的輸出：模型對、日誌錯的例子不少（輸入狂 → 輸入框）。
  整句質量以凍結評測集 `data/eval/sentences.tsv` 為準（見 `docs/notes/neural-rescoring.md`），回放只看詞級與個人學習。
- 2026-09-12 以前的日誌有一半是空的 `raw` 行（殼每次回車 / 失焦都調一次 `take_raw`），讀端要跳過 `keys` 與 `text` 都空的行。
- 回放裡原樣上屏（`raw`）也要走一遍 `take_raw`：個人英文詞（`gist`）與「這個串不糾」都是從那裡學的，跳過它英文首選低 10 個點（72.5% → 82.9%），
  那不是排序的問題，是尺子沒學。2026-09-12 起回放這麼做。
- 整句「不在候選」328 條的構成（2026-09-12）：16 條是 青簡（詞庫沒有的專名，個人詞該學但回放從零起）；294 條與現在首選同長、只是同音換字
  （184 條差一字、112 條差兩字：我之前 → 我只前、行的 → 型的、新寫的 → 新鞋的），這一類靠上下文分，歸神經重排與個人 n-gram，
  其中不少「選了」本身就是當時按空格接受的錯句（是按、所有喲偶、你先準備以下）；18 條長度不同，是切分 / 簡拼尾巴（準備以 ← `zhunbeiyix`）。
- 詞級沒命中 1208 條裡 742 條是 5 鍵以上、當時從詞候選裡選的短語（導航欄 / 候選框 / 我繃不住了 / 對齊），多半是詞庫缺詞而不是排序；
  最常重複的鍵是 `ba`（45 條，吧 / 把 看上下文）與 `wode`（34 條，詞庫缺 我的）。調常數救不了這兩類，要補詞庫與靠上下文模型。
