# 候選視窗設計

## 佈局

候選視窗預設豎排（配置 `[general] layout`，可選橫排）。豎排時每個候選項由兩個主要部分組成：

```text
候選詞                     翻譯
```

例如：

```text
1  計算機                  computer
2  電腦                    computer
3  計算                    calculate
4  計算器                  calculator
```

橫排可以展開成矩陣（2026-09-20，macOS；Windows 未接；開關 `[general] horizontal_grid`，預設關——它改了上 / 下、左 / 右、Esc 這幾個已有按鍵的行為，
不是每個人都要，關著時橫排下所有按鍵與以前一樣，改完立刻生效並收回單行）：單行時按上 / 下鍵立即展開並換行，矩陣是固定 6 行的視口（`GRID_ROWS`），
一行就是一頁候選，高亮移出視口上下邊緣時按行滾動，翻頁鍵一次翻一屏；左 / 右鍵在候選之間移動高亮（單行裡逐個移動、到頁邊自動翻頁但不展開，展開後按閱讀順序跨行；上 / 下鍵被矩陣佔了，單行裡只剩它們能挪高亮；拼音游標用 ⌥ / ⌘ + 左右），
數字鍵選高亮所在那一行，序號也只標在那一行；新一輪查詢或 Esc 收回單行。視口與移動規則在 Core `candidate::layout::Grid`（展示規則，各殼共用），
殼只轉發方向鍵、把視口裡的格子按行優先排進幀（`Frame::columns` 不為 0 即矩陣）。視窗尺寸在一輪查詢裡不變：
各列寬度由 Core 按**整份**候選估（`Grid::column_ems`：漢字一個字寬、拉丁字母 0.62、雲朵另加，單格封頂 `MAX_CELL_EMS` = 4 個字寬，
四字詞能完整顯示），不按視口裡可見的幾行實測，所以滾動、移動高亮時列寬不變；超出的候選截尾加「…」，高亮到它時網格下方的資訊行給出完整文本和譯文，
頁碼在資訊行末尾，資訊行放不下的同樣截斷，不撐開視窗；資訊行始終保留，在靠後的頁展開時視口往上補齊 6 行。9 列時網格最寬約 756 pt。
第一版按視口實測列寬、單格 6 個字寬，滾一行視窗就跳一下，最寬能到 1100 pt。兩條繪製路徑（`qingjian-render` 的 `renderer/matrix.rs`、系統繪製的 `view/matrix.rs`）同一套規則。

橫排時候選排成一行，只給高亮的那個在下面單獨一行顯示譯文（每個都帶譯文會把視窗拉得很寬），頁碼在行尾：

```text
1 計算機  2 電腦  3 計算  4 計算器          1/3
computer
```

頂部都有一行拼音（preedit），見下文「拼音行」。

## 視覺層級

- 候選詞：較大、較深
- 翻譯：較小、較淺
- 序號：弱化顯示
- 當前候選：輕量高亮

翻譯永遠不應該搶奪候選詞本身的注意力。它只是一個 annotation，而不是另一套候選系統。

## 翻譯 annotation 的規則

- 一個候選只顯示一條譯文，語言由使用者配置的 Learning Language 決定。
- 譯文缺失時該行留空，不顯示佔位符，不顯示「載入中」。
- 譯文尚未就緒時候選視窗照常顯示，譯文到達後再補畫，不等待。
- 譯文的具體取捨策略（詞典詞才標註、一詞多義取最高頻義項）見 [architecture.md](architecture.md)。
- **生詞**用強調色（橙）畫譯詞本身，不加圖示不加文字：一條譯詞在使用者上屏時出現在候選窗口裡的輪次不到 3（Core `FRESH_UNTIL`）就算生詞，
  看熟了自動變回譯文色。「看到」按上屏那一刻螢幕上那一頁算（殼每次畫完 `Engine::note_displayed` 告知當前頁，上屏時才記），
  逐鍵重新整理時一閃而過的不算。判斷與記錄都在 Core（`VocabularyTracker`，`Sense::fresh`），殼只是按 `Tone::Fresh` 換顏色；
  英文模式候選的中文釋義不是學習語言，不參與。

## 技術選型

候選視窗本質上只有四個原語：若干行 (序號, 候選詞, 譯文)、一行高亮、跟隨游標定位、非同步補畫譯文。
這麼小的 UI 不值得引入跨平臺 GUI 框架。預設由一個 Rust 自繪渲染器出點陣圖、各平臺只貼圖（主題因此畫素級一致），見 [rendering.md](rendering.md)；下表是各平臺視窗與退路的畫法。

| 平臺 | 方案 | 理由 |
|---|---|---|
| macOS | `objc2-app-kit`：非啟用的 NSPanel + 自定義 NSView，用 NSAttributedString / Core Text 畫行 | Squirrel 同款做法。視窗必須不搶焦點、浮在所有應用之上、瞬間出現，只有 AppKit 能穩定滿足 |
| Windows | Server 程序裡 GDI 畫到 layered window（`server/src/ui/layered/`） | 避開 WebView2 依賴（水杉 issue #68 就是安裝環境缺 WebView2）。原計劃改 Direct2D + DirectWrite，已被自繪渲染器取代 |
| Linux | 自繪視窗（wayland-client / x11rb），不用 IBus / Fcitx 自帶面板 | IBus 的 lookup table 沒有 comment 欄位，Fcitx5 有但樣式受面板限制。kime 走的也是自繪 |

macOS 面板的層級與 Space：層級 `kCGPopUpMenuWindowLevel`（101，與系統候選框同級；不能 `setFloatingPanel`，它會把層級改回 3，全屏應用裡就看不見），
collection behavior 是 CanJoinAllSpaces + FullScreenAuxiliary + Stationary。但 macOS 26 上 WindowServer 只把面板綁到它**建立時已有**的 Space：
登入時建的面板只在桌面 Space 上，之後新開的全屏 Space（Zed 全屏）裡沒有它，候選框留在桌面、全屏裡看不見（2026-09-07 用 CGS `CGSCopySpacesForWindows`
查實：面板的 Space 列表只有桌面那一個，同樣設定新建的面板卻是全部 Space；重設 collection behavior、收起再排前都不能讓它重算）。
所以每次 `orderFront` 後查 `isOnActiveSpace`，不在就把內容檢視搬到一塊新建的面板上再排前，並記一條 warn（`candidates/window.rs`）。
診斷指令碼在 `target/diag/spaces.swift` 一類的臨時位置，不進倉庫。

不選的方案及原因：

- **WebView（水杉 HTML UI 的路線）**：樣式最自由，但常駐程序多一個渲染引擎，首次彈窗有可見延遲，
  且引入平臺執行時依賴。候選框是「打字時每秒彈好幾次」的 UI，延遲比樣式重要。
- **egui / iced / GPUI 等 Rust GUI 框架**：它們假設自己擁有視窗和事件迴圈，
  和「非啟用浮層」這種系統級視窗語義打架，為幾百行繪製引入整套框架不划算。

主題化通過主題檔案（字型、字號、配色、行距、圓角、陰影、透明、漸變、佈局）實現，不提供 HTML/CSS 皮膚；主題渲染的方向見 [rendering.md](rendering.md)。

## 平臺層的職責

候選視窗由平臺層繪製，但候選內容、順序和譯文全部來自 Core。
平臺層拿到的是已經排好序、已經帶好 annotation 的候選列表，只負責畫。

## 按鍵約定（macOS 已實現，其他平臺照此）

| 按鍵 | 行為 |
|---|---|
| 字母、`'` | 在游標處插入 |
| 空格 | 上屏高亮候選；無候選時上屏拼音 |
| 1 到 9 | 上屏當前頁第 N 個。這一頁沒有第 N 格（`gpt6` 只有三個候選）時數字當內容進緩衝區：中文模式成為英文直輸段，英文模式接進單詞；雲端詞還沒到的佔位格、問字模式裡按了不算 |
| 回車 | 上屏拼音本身 |
| 退格 / Delete | 刪游標前 / 後一個字母 |
| ⌥⌫ / ⌘⌫ | 刪游標前一個音節（全拼按最優切分的最後一個音節連同 `'`，切不動的尾巴整個刪；雙拼兩鍵一音節；直輸段按字母段）/ 刪游標前全部拼音（`Engine::delete_syllable_backward` / `delete_to_start`）。不在組句時交給應用，撤銷的賬不再記（`break_chain`） |
| Esc | 清空 |
| 上 / 下 | 移動高亮，到頁邊自動翻頁；第一項再按上不動 |
| ⌥← / ⌥→ | 按音節跳游標（邊界規則同 ⌥⌫；`'` 跟著前面的音節，`Engine::move_cursor_syllable_left` / `right`）。游標在末尾發現前面的音節錯了：⌥← 跳過去、⌥⌫ 刪掉重敲、⌘→ 回末尾 |
| 左 / 右、Cmd+左 / 右 | 移動拼音游標（不切模式）。游標停在中間時候選只按游標前的拼音算（`ni|hao` 出 你），上屏後剩餘拼音留著、游標落到末尾；游標在開頭或末尾按整段算 |
| PageUp / PageDown、Shift+Tab、翻頁鍵對（配置 `[general] page_keys`，預設 `[` `]`，可選 `,` `.` 或 `-` `=`；選後者時組句中的 `-` 是翻頁、不再進英文直輸段） | 翻頁。每頁幾個由 `page_size` 定（1–9） |
| 半形標點（會轉全形的那批見 Core `punctuation::converts`，配成翻頁鍵的除外；⇧+數字已被刪候選 / 譯詞鍵截走） | 組句中分兩路。**會轉全形的**（`,` `.` `?` `!` `:` 等）：把高亮候選上屏、再接該全形標點，`nihao,` `dui'ma?` 一氣打完「你好，」「對嗎？」；數字後的 `.` 是否保持半形由 Core 判斷，Windows 關掉全形轉換時接半形。**不轉的**（`-` `/` `@`）：進入**英文直輸段**，`no-way` 整段原樣顯示，之後的可見字元（含數字、大寫）都追加，回車原樣上屏，空格原樣上屏後空格本身也交給應用，Esc 清掉。表示式 / 問字模式優先。`'` 是隔音符，任何模式進緩衝區。這樣有了「拼音 + 標點 = 上屏候選 + 全形標點」（`[general] punct_commits`，預設關：會轉全形的標點也進英文直輸段，與以前一致）；代價是組句中打不出「字母串 + 半形標點」（`hello, world` 改用英文模式，或 Windows 關掉全形轉換） |
| Tab | 有整句補全（雲聯想）時接受它；沒有則翻頁 |
| 修飾鍵 + 數字（⌥ / ⇧⌥ 上屏譯詞、⇧ 刪候選） | **只在組句中認**。不在組句時 ⇧4 就是普通的 `$`，走中文標點規則出 ￥（⇧1 ！、⇧6 ……、⇧9 ⇧0 （ ））；曾經在這裡被截走後原樣還給應用，全形轉換就漏了 |
| 按住 Shift 打的大寫字母 | 進拼音緩衝區，與小寫一樣參與匹配（`⇧C` + `pan` → C盤），拼音行按敲的樣子顯示大寫；原樣上屏（回車 / 無候選）時還原大寫。macOS 殼仍是「先把拼音原樣上屏，再把這個大寫字母交給應用」 |
| ⌥ + 1–9 / ⇧⌥ + 1–9 | 上屏當前頁第 N 個候選的**譯詞**而不是候選本身：⌥ 第一條，⇧⌥ 第二條（候選右側有兩個譯詞時）；日文不帶注音；學習與拼音消耗同選了那個候選。沒那條譯詞的候選吞掉按鍵不動。兩組修飾鍵在配置 `[shortcut] translation` / `translation_second`（任意修飾鍵組合，偏好設定「快捷鍵」頁點按鈕錄製），兩組相同或為空整個退回預設；說明裡提醒避開 ⌃+數字（系統切桌面）和 ⌘+數字（應用切標籤頁）。控制器在 `handleEvent:client:` 裡按鍵碼認數字（修飾鍵會把數字變成 ¡™£），其餘按鍵自己分發成 `handle_text` / `handle_command`。不能改用第二層協議 `inputText:key:modifiers:client:`：那會把回車、方向鍵當文本送來 |
| ⇧ + 1–9（可改） | **刪掉當前頁第 N 個候選**：自己造的詞、雲端選過的詞（使用者詞）整個刪掉，本地不再出；詞庫裡的詞清掉對它的全部學習（選擇次數、各輸入串下的選擇、個人 n-gram 裡與它有關的轉移），回到原來的排序；整句 / 快捷候選 / emoji 沒什麼可刪。刪完重新查一遍，結果那句話（「已刪除使用者詞「X」」）灰字顯示在拼音行右側，敲下一鍵就沒了；那格沒有候選就吞掉按鍵。修飾鍵在 `[shortcut] delete_candidate`（預設 ⇧，與譯詞鍵撞了退回預設）。代價是組句中 ⇧1 不再是「上屏 + ！」，要先上屏；Core `Engine::forget` → `Learner::forget` / `forget_english` |
| ⌃⌥T（可改） | **翻譯選中的文字**：不在組句中、應用裡有選區（≤ 500 字元）時，把選區交給雲端翻譯（`PredictionKind::Translate`，`Engine::request_translation`）：選區主要是漢字譯成學習語言，有假名或拉丁字母不少於漢字就譯成中文（Core `prediction::translation_target` 按字元統計定方向，提示詞兜底「已是目標語言就譯成中文」），候選視窗先顯示「翻譯中…」，譯文到了作為唯一候選顯示；回車 / 空格 / 1 用譯文替換選區（`insertText:replacementRange:`），Esc 保留原文，其他鍵放棄並照常交給應用。雲服務關著、密碼框、應用不支援讀選區（部分 Electron）時快捷鍵原樣交回應用。快捷鍵在 `[shortcut] translate_selection`（修飾鍵 + 一個字母或數字，任意組合，偏好設定「快捷鍵」頁錄製；預設 ⌃⌥T 避開了 ⌘T 這類應用常用鍵） |

### 整句轉換（離線）

最優切分至少兩個音節、且最優路徑不止一個詞時，整句放在第一位（空格上屏的就是它），`CandidateKind::Sentence`：
`jintiantianqihenhao` → 今天天氣很好，`womenyiqiqukaifa` → 我們一起去開發。整段本身是詞庫裡的詞時不出整句。
打分是靜態 bigram（`qingjian-lm`）與個人 n-gram（二元 + 三元，看前兩個詞）插值。簡拼位置照轉（`jttqhh` → 今天天氣很好，`wjdzjsg` → 我覺得自己是個），
每個簡拼格子按字首多留一些詞、由語言模型挑讀音；兩字母簡拼多半還是詞（`sj` 時間），單詞路徑得分高就不出句子。
全拼句子末尾未打完的音節至少兩個字母才算進句子（`woxiangs` 多半是沒打完的 shuo），前面已有簡拼的句子末尾單字母就是一個音節（`wxq`）。
有音節連單字都查不到（只能拿拼音佔位）的不出句子；英文詞的位置看 `Engine::chinese_first`（配置 `[general] chinese_first`，預設關）：
關著時整段是英文詞或不像拼音帶出的英文補全排在句子前面（`hello` 先英文再 荷蘭咯）；開著時整句先插、英文詞緊隨其後排第二（`hello` 先 荷蘭咯 再 hello）。
預設關是回放定的：9241 詞 / 269 條英文上屏的凍結日誌上，預設開英文首選 82.5% → 7.1%，常在中文模式裡打英文詞的人被明顯傷到；關著與改前完全一致。
上屏按音節消耗拼音，路徑上的詞逐條記進個人 n-gram（`user-ngram.tsv`），不記詞頻。

**句末英文詞**（`Engine::split_english_tail`，`query::EnglishTail`）：整段末尾是英文詞表裡的詞、前面能切成完整拼音時，
整句是頭段的轉換加上那個詞（`woxiangxuehaorust` → 我想學好rust），排第一，`Query.tail` 是尾段字母（拼音行 `wo'xiang'xue'hao'rust`），
詞級候選只按頭段查。整段字母根本切不成拼音的（`wodetv` 的 v、`woyongvim`）直接按英文讀；整段也能讀成拼音的
（`woxiangxuehaorust` 讀成 … ru s… t… 簡拼、`wodedatabase`）兩種讀法比分：頭段整句分 + 英文詞 log 機率（wordfreq Zipf 換算，
沒詞頻按 Zipf 3）− 切換代價（`ENGLISH_SWITCH_PENALTY` 3 nat，拍的）要高過整段按拼音讀的整句（`sentence::convert_whole`，
末尾單字母也讀，`huoz` → 或者，兩邊覆蓋同樣多的字母才公平），贏了英文讀法排第一、拼音讀法第二，輸了英文讀法不出
（`womenqubeijing` 只有 我們去北京，`diaoyong` 不出 掉Yong）。尾段自己是完整拼音的（`fan`）要至少 4 個字母，
兩個字母的尾段只認縮寫詞（ID / TV）和個人表裡的詞；整段是英文詞（`agent`）、拼音不像話時能糾錯（`shiide` → 是的）或有英文補全
（`releas`）的不切。同時滿足的取最長尾段。上屏時英文詞是路徑上最後一個詞（音節就是敲的字母），進個人 n-gram，
並記進個人英文詞表。回放（2026-09-08，4867 條）與改前持平：詞 86.0% / 整句 89.3% / 英文 69.8%。
只認句末，夾在中間的英文（`wozaidebugzhege`）要等詞圖上加英文邊。

**越用越像自己**：連續上屏的詞（整句裡的、或一個個選的）都記成「前詞 → 後詞」，同時記「前二詞 前詞 → 後詞」；`qingjian` 裡選過兩次 青 + 簡，
再打 `qingjian` 整句就直接出 青簡（個人轉移壓過靜態模型裡的 請見）。三元分辨二元混在一起的接續：「我想」後面選過幾次 區，
`woxiangqu` 就出 我想區，而「不想」後面照舊。標點、回車上屏拼音、切應用都斷句，之後的詞按句首記。
**自動造詞**：自己連著選出的兩個詞合起來詞庫裡沒有（不超過 4 個字），同一段拼音裡連著選兩次、或分兩段打三次，
就記成使用者詞（`user-words.tsv`），之後按詞出、靠選擇次數排前。

### 英文模式候選

Caps Lock 亮著（英文模式）敲字母時也組詞：字母（以及組詞中的數字、`_` `'` `-`）進緩衝區、原樣顯示，候選來自英文詞表
（Core `english::suggest`）：整段正好是的詞第一（按詞表寫法），然後是字首補全，4 個字母起再給差一處編輯（換 / 多 / 少一個字母、相鄰對調）的糾正
（`recieve` → receive，`seperate` → separate）；後兩組各按選過的次數、詞頻排。大小寫跟著敲的走：`Compa` 出 Company，`COMPA` 出 COMPANY。
帶數字或符號的（`foo1`）是識別符號，不猜。emoji 照配，但排在所有詞後面（上下鍵選詞時不擋路）。

選詞與中文模式一樣：**空格選高亮、數字選當前頁第 N 個、翻頁鍵翻頁**，上下鍵動高亮，Tab 也選高亮項；詞上屏後空格照樣交給應用，後面接著打下一個詞。
有候選時數字才選詞，沒候選（`kubectl` 這類詞表沒有的詞）時數字是識別符號的一部分。**回車、標點原樣上屏敲的字母**（再把那個鍵交給應用），
詞表沒有的寫法靠回車。0.1.3 之前空格只在動過高亮之後才選詞、數字一律是數字，理由是不讓詞表沒有的詞被補全替換，
但測試者按直覺都拿空格和數字選詞，2026-09-16 改成與中文一致。Esc 清掉，退格刪字母。英文模式不發雲聯想；回車原樣上屏也不記「不糾這個串」。
組詞中 Caps Lock 滅了先把字母原樣上屏。配置 `[general] english_candidates = false` 關掉候選，回到純直通；偏好設定裡有勾選框。

**按應用給（白名單）**：只有 `[apps] english_candidates_on` 列出的應用（macOS 按 IMK 客戶端的 `bundleIdentifier`、Windows 按宿主 exe 名、
Linux 按 Fcitx5 的應用名，`*` 結尾按字首匹配）裡英文模式給候選，其餘是純直通，字母原樣交給應用。預設名單是瀏覽器、聊天、辦公與筆記這類寫成段文字的應用。
2026-10-10 從黑名單（`english_candidates_off` 列終端 / 編輯器）改成白名單：Photoshop 畫布上的 W / H / V 單鍵快捷鍵被英文組詞吞掉，
設計、3D、CAD、影片剪輯、遊戲都靠單鍵快捷鍵，黑名單列不完，而英文補全只在寫成段文字的地方有用。
`english_candidates_off` 留作排除：`english_candidates_on = ["*"]` 處處都給，再排除幾個。認不出應用時只有 `"*"` 給。
偏好設定「通用」頁一個勾選框「只在瀏覽器、聊天和文件類應用裡給」：勾上寫預設白名單、去掉寫 `["*"]`，改過名單的勾一下就回預設。
全域性開關關著時這一項不起作用。開著詳細日誌時切到應用會把它的 bundle identifier 記進日誌，往名單里加就照抄。
`[apps]` 分節以後按應用定 preedit 模式等也放這裡。

**個人英文詞表**（`user-english.tsv`，`詞\t次數`）：隨包詞表只有兩萬多詞，`gist`、`kubectl` 這類不在裡面的詞以前永遠出不了候選。
現在原樣上屏的字母串只要像英文詞——純字母、至少兩個，中文模式下還要**切不成完整拼音**（`hao` 回車多半要的是字母本身，不學；
`gist` / `python` / `hello` 切不乾淨才是英文）——就記進個人詞表，選中英文候選也記。英文候選由個人表 + 隨包表一起出，
個人表在前：精確詞取第一個有的，補全與糾正合在一起按選過的次數、詞頻排（`Engine::english_lists`、`english::suggest` 收詞表列表）。
所以 `gist` 回車一次，下次敲 `gist` 它就是首選。

### 英文補全與 emoji

- **英文補全**：整段輸入切成的拼音「不像話」（切不動、或非末尾有簡拼 / 殘缺音節：`compa` → `co'm'pa`、`impor` 連第一個字母都切不動）
  且至少 3 個字母時，除了整段正好是的英文詞，還出詞表裡該字首下最常用的 3 個（`compa` → company / companies / compared），
  緊跟在精確詞之後、排在拼音候選前。乾淨的拼音（`xian`、`shan`）不補全，免得每個音節都冒英文。詞頻來自 wordfreq（`tools/corpus/english_frequency.py`）。
- **emoji**：前 5 箇中文 / 英文候選裡有配 emoji 的，emoji 緊跟在那個詞後面（`ku` → 哭 😢 😭，`smile` → smile 🙂 😊），右側標註對應的詞；
  每個詞最多 2 個、一次最多 3 個，`CandidateKind::Emoji`，上屏按那個詞的音節消耗拼音（英文詞帶出的對應整段輸入）、不記學習。
  資料是 Unicode CLDR 中文與英文 annotations（`assets/emoji/emoji-zh.tsv`、`emoji-en.tsv`，Unicode License v3，可釋出，載入時合成一張表），
  `dict-convert emoji --language zh|en` 生成：單字詞只收名字裡含這個字的 emoji，名字裡含這個詞的靠前、名字越短越靠前。
  日文表要等有日語輸入模式再說。

### 模糊音（預設全關，`config.toml` 的 `[fuzzy]`）

開了 z/zh 之後敲 `zi` 也出 知 / 之，開了 n/l 敲 `lan` 也出 南，開了 f/h 敲 `kaiha` 也出 開發；韻母 an/ang、en/eng、in/ing
只對完整音節生效（末尾沒打完的音節本來就按字首查，`fen` 自然出 feng 的字）。敲對的詞仍然優先：模糊命中的詞頻減半參與排序，
同分排在後面。簡拼位置也套聲母規則（`zh` 字首開了 z/zh 就按 `z` 查），整句轉換用同一套寫法。
CLI 用 `--fuzzy z-zh,n-l` 或 `--fuzzy all` 臨時開。

### 雙拼（預設關，`[general] shuangpin`）

七套方案：小鶴（`xiaohe`）、自然碼（`ziranma`）、微軟（`microsoft`）、搜狗（`sogou`）、智能ABC（`abc`）、小浪（`xiaolang`）、首道（`shoudao`）。鍵位表在 Core `shuangpin::table`，
按 Rime 的 `double_pinyin*.schema.yaml` 核對（搜狗來自 rime-ice 的整理，小浪來自使用者提供的搜狗小浪雙拼與 Rime 配置，智能ABC 按公開鍵位資料核對，首道按作者倉庫 shoudaoshuangpin/shoudaoshouyouplus 的鍵點陣圖、並與永珍拼音的拼寫運算對過），每套方案對全部音節做往返測試；微軟與搜狗只差微軟的 `v` 鍵兼作 üe。
開著時緩衝區裡存的仍是敲的鍵，Engine 在切分前把鍵兩兩配對解成全拼（音節之間自動帶 `'`，沒有切分歧義），
之後查詞、整句、雲聯想、學習全部走全拼那一套：拼音行顯示解出來的全拼（`nihc` → `ni'hao`），學習按全拼記（`user-choices.tsv` 的鍵與全拼共用，切回全拼也受益），
上屏消耗按「候選蓋住幾個音節、每個音節幾個鍵」換算回緩衝區（`kdfave` 選 開發 吃掉 4 個鍵，剩 `ve`）。
末尾落單的一鍵當聲母 / 母音前綴出簡拼候選（`kdf` → kai f…）；配不出音節的鍵起原樣留作尾巴（`nibl` → `ni'bl`）。
零聲母：小鶴 / 自然碼寫 `aa` `ai` `ah`（a、ai、ang）一族，微軟 / 搜狗寫 `o` + 韻母鍵（`oa` `ol` `oh`），雙寫母音的寫法也認。智能ABC 只認 `o` + 韻母鍵，`aa` / `ee` 解為 zha / che。
微軟 / 搜狗的 `;` 是 ing：組句中末尾有落單聲母時敲 `;` 進緩衝區（`x;` → xing），其他時候仍是標點，殼問 `Engine::takes_semicolon`。

雙拼下 v / u / i 都是音節鍵，模式鍵換成對應的大寫字母（`ModeKeys::shifted`，搜狗 / 微軟雙拼的做法）：中文模式、沒在組句時 `Shift`+`V` / `Shift`+`U` 進表示式 / 問字，
緩衝區裡存的就是大寫字首（`V1+2`、`Unihc`），之後與全拼下的 `v` / `u` 同路；殼問 `Engine::takes_mode_letter`。Windows 的 DLL 不知道雙拼開沒開，`Shift`+`V` / `U` / `I` 一律送 Server，全拼下 Server 回放行、由 DLL 自己插入。拼寫糾錯停用：敲錯一鍵換掉的是整個聲母 / 韻母，
全拼的一處編輯模型不適用。回車仍原樣上屏敲的鍵；全部鍵都能解成完整音節的串（`nihc`）不記進個人英文詞表，解不乾淨的（`gist`、`hello`）照記。
快捷候選（`rq` `sj` `xq`）與英文候選仍按敲的鍵認。
已知：`lue` / `nue` 與 `lve` / `nve` 同鍵，解成 v 的寫法，詞庫裡少量 `lue` 讀音的詞雙拼下打不出（待把詞庫統一成 v）；`lo` 與 `luo` 同鍵，解成 luo。

### 快捷候選（搜狗 v 模式）

Core `shortcut` 模組，不查詞庫、由輸入直接算出，`CandidateKind::Shortcut`，上屏吃掉整段作用域、不記學習：

- `rq` / `sj` / `xq`：今天的日期（`2026年9月3日`、`2026-09-03`、`2026/09/03`）、現在的時間（`19:06`、`19:06:23`、`19點06分`）、
  星期（`星期四`、`週四`），插在本地首選之後（首選仍是 日期 / 時間 / 需求 這類詞庫詞）。
- 表示式鍵（預設 `v`）開頭進**表示式模式**：不解析拼音，preedit 原樣顯示。`v1+2` 出 `3` 與 `1+2=3`（支援 `+ - * x / ^`、括號、小數），
  `v123` 出中文數字小寫 `一百二十三` 與大寫 `壹佰貳拾叄`，再跟金額 `一百二十三元整` / `壹佰貳拾叄元整`；
  `v123.5` 出小數讀法 `一百二十三點五` / `壹佰貳拾叄點伍` 與金額 `一百二十三元五角` / `壹佰貳拾叄元伍角`（小數超過兩位只有讀法，`shortcut::number_forms`）。此時**數字和運算子進算式而不是選詞 / 翻頁**，
  選第二項用上下鍵 + 空格；回車上屏原文；`v` 開頭的英文詞（`very`）仍走中英混輸。表示式模式不發雲聯想。
- 問字鍵（預設 `u`）後跟十六進位制碼點出那個字元：`u4e00` → 一，`u+1f600` → 😀（全是十六進位制且含至少一個數字，或以 `+` 開頭；
  `uface` 這種純字母沒有 `+` 當拼音問題）。本地直接答、不問雲端。

模式鍵在 `[shortcut]` 分節配置，只能是 `v` / `u` / `i`（三個不能開頭拼任何音節的字母，搜狗 / 微軟同一思路：
一鍵進模式、不要修飾鍵、中文模式下零衝突）且互不相同，非法組合整個退回預設。
沒采用水杉的 Shift+字母模式鍵：Shift+字母留給「臨時打大寫」（Windows 上它是進拼音緩衝區、按小寫匹配、原樣上屏時還原大寫），而且 Shift 單擊留給切中英。

### 雲聯想（預設關閉，配置開啟）

組句中停鍵 300 ms 後，雲端給出的**詞**（如 `zhangtao` 在財務上下文裡的 賬套，或糾錯後的 `zhgdoima` → 這個東西嗎）
補進候選視窗**第一頁末尾**（`[predict] slots`，預設 2：每頁 9 個時就是 8、9 兩格），前面帶雲朵，數字鍵照常選，
上屏吃掉整段拼音；本地首選仍在第一位，空格上屏的還是它。選中詞庫裡沒有的雲端詞，它會記成使用者詞，下次本地直接出。

請求裡帶：敲的字母、本地切分、游標前後文本（64 / 32 字）、本地整句轉換的結果（`guess`）和本地前 5 個候選。後兩樣在提示詞裡明確標成
「本地的猜測，可能全錯，只用來告訴你本地已經能給什麼」，模型按字母與上下文獨立判斷、只給本地給不出或排錯的詞，沒有就給空陣列
（之前模型愛照抄本地第二個候選，`zhangtao` 回一個 張韜，等於沒用）。

**簡拼不問詞，只問整句補全**（2026-09-16）：切分裡半數以上音節是縮寫（`fhyq` → 符合要求）時請求的 `max_items = 0`，
只有 `sentence` 那一路要結果（Core `prediction::mostly_abbreviated`；問字模式的答案不受這條限制，答案本來就對不上問題的拼音）。
原因是日誌實測：模型按聲母湊出來的詞大多是生造詞（複合語氣、符號對映、不態、步太），而拼音校驗按「首字母序列匹配」放行縮寫輸入
（`nei rong` 對 `nr`、`fu he yu qi` 對 `fhyq` 都算過），攔不住；整句那一路質量本來就明顯更好（`fhyq` → 符合要求的話我們就按這個方案執行）。
提示詞同時加了三條硬規則：不要按縮寫拼湊詞、不要生造詞、不要給與本地首選同音的變體。字母門檻仍是 2（`nr` 這類兩字母請求照發，
它們的用處在整句與糾錯，不在詞）。

位置規則（Core `CandidateLayout`，殼只照著畫）：雲端詞到了才補進第一頁最後幾格，原來那幾格的本地候選挪到下一頁；
前面的本地候選**一格不挪**——之前雲端詞插在第二位，使用者看著 2 號按下去的瞬間被頂掉、選錯，這是改的原因。**不預留、不畫佔位**：
沒到、沒詞、超時都什麼都不變，頁面上只會「多出幾個詞」這一種變化（預留槽位加灰色佔位的做法試過，雲端常常空手而歸，
佔位出現又消失反而鬧眼睛）。使用者已經翻到後面的頁、或高亮已經移到末尾會被挪走的那幾格時，到的詞丟掉不補。
雲端詞比格數多隻取前幾條；與本地候選同文的不要（本地已經能給）；雲端詞只在第一頁，翻頁後全是本地候選。`slots = 0` 不要雲端詞、只要整句補全。
問字模式沒有本地候選，答案從第 1 格起排滿一頁。

### 問字模式（雲聯想的一部分，問字鍵 `u` 或 `?` 開頭）

緩衝區為空時敲問字鍵（預設 `u`）或 `?` 進問字模式，接著用拼音敲問題：`usangemushishenmezi`（三個木是什麼字）、`umumumu`（報部件）、
`ufaguoshoudu`（短事實問答）。`?` 在任何配置下都是別名，也是英文模式（Caps Lock）下唯一的入口（`u` 在英文模式裡就是字母 u）。
本地不出候選，preedit 顯示 `usan'ge'mu…`，停鍵後雲端答字或短答案，
帶雲朵與帶聲調讀音（森 sēn），數字鍵選中上屏、吃掉整段。答案不做拼音校驗（它本來就對不上問題的拼音）。
請求裡除了字母與切分還帶 `question`：本地整句轉換把問題拼音轉成的漢字（`PredictionRequest::guess`，可能錯字），模型據此理解問題；
提示詞強呼叫戶是打不出這個字才來問的，**只答被問的字、不復述問題**。模型仍把問題整句寫回來時（`?sangezhishishenmezi` 曾答 三個直是什麼字），
Core 按 `prediction::restates_question` 剔掉：與本地轉出的問題相同、包含它的後半截、問題不短而答案一樣長、或答案裡帶疑問詞。
中英文模式（Caps Lock）都能進：`?` 後面緊跟的不是字母（回車、空格、標點、方向鍵）就還原成問號上屏
（中文模式全形 `？`、英文模式半形 `?`）。回車和空格只做「把這個問號上屏」、鍵本身吞掉（否則聊天框裡回車會連訊息一起發出去、
空格會多一個空格），標點和方向鍵還原後再交給應用；退格 / Esc 清掉。英文模式下 Caps Lock 送來的大寫字母按小寫收進問題。
沒開雲聯想時 `?` 仍然進問字模式但等不到答案，回車上屏原文；離線拆字版（IDS 資料）待做。
同一次請求還給一條「☁ 整句」，畫在 preedit 右側：它是以這個詞開頭的完整說法（`suoyiwoxiangq` → 所以我想去吃飯），
替換整段拼音，Tab 接受，繼續敲鍵就換掉。有應用上下文時整句接著上下文寫；沒有也給最常見的說法。
接受的整句沒有拼音，記不了詞頻與使用者詞，但會按語言模型切成詞（Core `sentence::segment_text`：文本子串上的 Viterbi，模型認識的子串才算詞，
標點處斷句）逐條記進個人 n-gram，與選整句候選一樣；整句退格刪光、同一段拼音重選時這些轉移一併退回。沒接語言模型時不記。
上屏之後不聯想。

答案怎麼進候選：問字沒有本地候選，`CandidateLayout::capacity` 把整頁都給雲端；殼補雲端詞前的「別挪走使用者正看著的候選」保護
（不在第一頁、或高亮落在末尾雲端格上就不補）對沒有本地候選的情況必須放行，否則 `page_size - capacity = 0` 會把所有答案丟掉
（2026-09-07 修過，`host::cloud_slots_untouched`）。聯想執行緒的快取不存空回覆，否則第一次沒答上來的問題重打也永遠是空。

雲聯想的條目用雲朵圖示和不同顏色區分，永遠只是本地候選之外的補充：本地候選的位置與順序都不因它變。
選單欄「中 / 英」後帶 ☁︎ 表示聯想開著、上下文會發往雲端；Secure Input 裡絕不傳送。

### 拼音行（preedit）

候選視窗頂部有一行 preedit：帶 `'` 的切分拼音和我們自己畫的游標。marked text 裡的插入點由應用決定畫不畫，
終端和不少 Electron 應用不畫，所以游標必須自己畫。
Core 給的是分段（`Query::marked_segments`，`MarkedKind`：敲的拼音 / 游標後剩下的拼音 / 被糾錯改掉的字母），
殼按段選樣式（剩餘部分畫淡，糾錯改掉的畫淡加刪除線），游標位置按拼接後的字元數算。

### 拼寫糾錯

拼音「不像話」時（切不乾淨有尾巴，或非末尾的音節裡有簡拼 / 殘缺）試一處編輯：相鄰換位、換一個字母、多一個、少一個；
末尾是單字母時（`mingtai'n`，可能是合法簡拼也可能是敲反了）只試相鄰換位。只保留改完後每個音節都完整的變體；
相鄰換位的變體另放寬到「只有末尾一個音節沒敲完」（2026-09-15，`correction::loose_segmentation`，按解析器偏好取第一種切法：
`mignt` → `ming t…`、`migntia` → `ming tia…` 而不是 `ming ti a`），敲反兩鍵的人多半還在往下敲，候選按前綴出 明天，不用等詞敲完；
編輯落在沒敲完的末尾音節裡時不記個人敲錯表。這類變體只在湊不出「每個音節都完整」的變體時才參與：殘尾按字首能匹配到高頻詞，
得分往往壓過整段完整的糾正（凍結日誌回放裡 `keyyi` 從 可以 變成 `ke yi y…` 的 可以有），所以有完整變體就只在完整的裡挑；
末尾落單單字母的完整變體不算數（`migntia` 換一個字母能湊出 `mian ti a`，正是可疑切法），只有一個音節的、或改在剛敲的最後一個鍵上的（換掉最後一個字母 / 末尾補一個字母，`Edit::touches_last_letter`）也不算數
（`zehg` 換掉 h 是單音節的 `zeng`、換掉剛敲的 g 是 `ze ha`，四個字母以上只拼出一個音節或還在改最後一個鍵，多半是還沒敲完），
否則 `ming tia…` / `zhe g…` 會被它們擠掉。
合成樣本（600 高頻詞 × 各類敲錯，2026-09-17）：換位後敲到一半的首選 2.4% → 23%、前五 17% → 42%，整詞各類持平，敲對的對照組零誤糾。
再按噪聲通道挑：每個變體跑一次整句轉換，糾正之間比較時相鄰換位便宜 `correction_transpose_discount`（1 nat：一個位置只有一種換法、卻有七八個相鄰鍵可換錯，
`mignti` 換位成 `mingti` 勝過換字母成 `mianti`），得分最高的那個還要**扣掉一次編輯的代價（`TypoCosts::correction_penalty`，5 nat，這一步不打換位折扣，
否則 `zhongwne` 原樣的 中午那 會被 中文 壓掉）後仍高於原串按原樣轉出的得分**才糾
（`nihooma` → 你好嗎，`woxiagnqu` → 我想去，`mingtain` → 明天，`nihaov` → 你好；原串切不乾淨就沒有原樣得分，能轉出整句的糾正直接勝出）。
合法簡拼（`nhao`、`womend`）原樣與糾正後走的是同一條路徑，扣掉代價就輸了，不會被誤糾；
整段本身是英文詞的不糾（`hello` 不會變成 和咯）；「刪掉剛敲的最後一個字母」不算糾正（`kaiv` 的 v 留作尾巴）；少於 4 個或多於 24 個字母不糾。
2026-09-05 之前的規則是「糾正後至少湊出一個兩音節詞」，語言模型把 你/好/嗎、我/想/去 都切成單字路徑，這條規則反而放行了 你/後媽、我/峽谷/區，已廢。

**詞圖裡的敲錯邊**（2026-09-06）：上面那路只管切不乾淨的輸入；全部音節都合法、整句卻說不通的（`meiganxi` 沒敢洗）另有一路——
整句詞圖裡每個完整音節除了敲的原樣，還按它的一處敲錯變體（相鄰兩鍵換位 `shou`→`shuo`、敲到相鄰鍵 `ni`→`mi`、多一鍵 `gang`→`gan`、少一鍵 `gan`→`guan`；
`correction::typo`，只算合法音節，不算不相鄰的鍵）查詞，命中的詞扣那類敲錯的代價（換位 / 相鄰鍵 5 nat，多鍵 / 少鍵 5.5，`TypoKind::cost`）。
Viterbi 按噪聲通道挑路徑：`meiganxi` 讀成 沒關係 只扣一次 5.5，仍高於 沒/敢/洗 三個單字，就出 沒關係；`meiganxie` 沒感謝 原樣說得通，不動。
詞級候選**不**帶敲錯變體（`kaif` 會冒出 咖啡 擠掉更長的原樣詞），整句路徑讀出的一個詞（沒關係）作為詞候選插到最前；
詞級候選裡有音節正好拼成整段輸入的詞時不許敲錯邊壓過它（`jineng` 按 `jin'eng` 切時詞圖裡讀出 近藤，但 技能 正好拼成 `jineng`，退回原樣路徑）。
不到 4 個字母、雙拼、非末尾帶簡拼的切分、整段一處編輯已生效的糾正後拼音都不加敲錯邊。
上屏時候選音節逐個對回敲的字母（`Engine::align`：原樣、沒打完、模糊音或敲錯變體、公共字首——沒打完排在變體前，`shijia` 選 時間 不算把 `jian` 敲成 `jia`；先找能把每個音節都對上的對齊，帶回溯——
`pingyin` 上屏 拼音 時 `pin` 原樣只吃三個字母會剩下 `gyin`，退回來按 `ping` → `pin` 吃四個，2026-09-17），按敲的字母消耗，
靠敲錯變體對上的 (敲的, 要的) 音節對記進**個人敲錯表**（`user-typos.tsv`，`Learner::record_typo`），退格重選時退回；
接受整段一處編輯的糾正也記（編輯落在的那個音節，`Correction::typo_pair`）。以後那條邊的代價按 min(ln(1 + 次數), 3) 打折，
整段糾錯的編輯代價同樣打折——習慣性把 `shuo` 敲成 `shou` 的人，幾次之後 我說 就自然排上來。這就是「個人按鍵混淆模型」，不訓練、線上計數。

糾正生效時候選全部來自糾正後的拼音，拼音行把被改掉的原字母畫成刪除線插在原位：`ni'h` ~~o~~ `ao'ma`；
選詞按糾正後的音節消耗拼音，再按那處編輯換算回原串（多敲的字母跟著被吃掉）。**回車仍原樣上屏** `nihooma`。
學習：選了糾正後的詞按原輸入串記選擇（`user-choices.tsv`），下次同樣敲錯直接首選；回車原樣上屏過的串記成 `<raw>`，以後不再糾它。
Core `correction` 模組只產生候選糾正，挑選與學習在 Engine 裡。

**輸入日誌**（`[general] input_log`，預設開）：每次上屏往資料目錄的 `input-log.jsonl` 追加一行——`keys`（消耗掉的原始鍵）、`pinyin`（整段切分，糾錯時是糾正後的）、
`corrected`、`text`、`source`（word / cloud / sentence / english / shortcut / emoji / raw / translation / cloud_sentence）、`index`（選的是查詢時候選列表裡第幾個，
晚到的雲端詞與原樣上屏為空）、`top`（查詢時前 5 個候選）、`scheme`、`english`、`t`（本機時間）；退格撤銷另記一行 `retract`，指回被撤銷那條的 `id`。
只有敲的鍵與上屏的文字，不含應用裡的上下文；只寫本機，「進階」頁可關可清，「關於」頁隱私說明有寫。用途：離線回放算首選命中率做排序 / 整句的迴歸評測，
以及個人模型（Phase 7）的訓練對。回放工具是 CLI `--replay`（見 CLAUDE.md），首批 150 條：詞首選 75%、前五 95%，整句首選 86%。Core `Engine` 在 `query` 時留摘要（`QuerySnapshot`）、上屏時湊成 `InputLogEntry` 交給 `InputLogger`（學習 crate 的 `InputLog` 落盤，攢 20 條刷一次，停用輸入法時也刷）。

選錯了詞也有補救：上屏後馬上把它整個退格刪掉、重打同一段拼音換選別的詞，上一次記的學習（選擇次數、輸入串選擇、詞轉移）會退回去，
不用擔心一次誤按空格把錯詞教給輸入法。

拼音顯示在哪由 `[general] preedit` 定：`both`（預設）行內 marked text 與視窗頂部都顯示；`inline` 只在行內，視窗不帶拼音行
（雲聯想的整句補全仍在視窗頂部單獨一行）；`window` 只在視窗，應用裡放空的 marked text——終端與部分 Electron 應用行內拼音畫得難看時用，
游標矩形仍從應用的插入點取（macOS 拿插入點，Windows 拿當前選區）。

Windows 上這條設定由 Server 讀、隨 `Frame.preedit_mode` 下發（2026-09-16）：DLL 按 `inline()` 決定要不要起 TSF 組句，
Server 按 `in_window()` 決定視窗頂部畫不畫拼音行；幀裡始終帶著拼音分段，兩邊各取所需。`window` 模式下應用裡沒有組句範圍，
游標矩形改從 `GetSelection` 的插入點量（`com/edit/anchor.rs::caret_rect`），一段組句裡問一次輸入框狀態（私密 / 游標前文）
靠 `Shared::context_reported` 記賬，不以「組句剛起」為準。

組句期間其餘編輯動作一律吞掉，否則應用會動游標、丟 marked text。
