# 效能：做過什麼、怎麼找到的、為什麼這麼改

輸入法的效能預算只有一條：**每一鍵的候選必須在 10 ms 內算完**（使用者敲鍵間隔 100 ms 上下，超過 30 ms 就能感覺到黏），
啟動儘量 1 s 內。聯想走後臺執行緒不算在內。這篇按時間順序記每一輪最佳化：起因、怎麼定位、改了什麼、數字前後對比，
以及走過的彎路。數字都是 release 構建、開發測試詞庫（89 萬條）、300 萬對 bigram 的 M 系列 Mac 上量的。

## 怎麼量

- `cargo run --release -p qingjian-cli -- <拼音>` 打每個階段的耗時：parse（切分 + 糾錯）、lookup（詞庫查詢）、
  rank（排序 + 各類插入，整句轉換算在這裡）、translate（釋義查表）。
- `--typing` 逐鍵模式（2026-09-05 加）：把 `kaifa` 當 k、ka、kai、kaif、kaifa 五次按鍵，每個字首查一次並標註譯文，
  一行一鍵。這才是輸入法的真實工作量，一次性查整段會漏掉「首鍵最貴」「簡拼越敲越貴」這類問題。
- 啟動日誌帶各資料檔案的載入耗時（`載入完成 dict_ms=… glossary_ms=…`、`語言模型已載入 load_ms=…`、`Engine 就緒 total_ms=…`）。
- 定位熱點靠**臨時打點**：在懷疑的函數里 `Instant::now()` 累加、`eprintln!` 打出來，看完刪掉。機器上沒有裝 profiler，
  而且 IME 程序也不方便掛 profiler；打點夠用，前提是先打點再改（見下面的彎路）。
- 測試效能改動不改行為：詞庫查詢有一份線性掃描版只在測試裡用，隨機詞庫 + 隨機模式與收窄版對拍，結果集必須相同；
  排序 / 整句的改動靠現有單元測試和 CLI 上一組固定輸入迴歸。

## 第一輪：記憶體（2026-09-03）

**起因**：詞庫從幾十條樣例換成 89 萬條真實資料，程序 RSS 480 MB。每條詞一個 `String` + 一個 `Vec<String>` 音節，
分配器開銷和指標比資料本身還大。

**改法**：arena + 偏移。所有詞文本首尾相接放一個 `String`（`texts`），所有拼音鍵放另一個（`keys`，同音詞共用一個鍵），
索引是兩個 `Vec` 的定長結構：`KeyIndex { key_start: u32, key_len: u16, first_slot: u32, slot_count: u32 }`、
`Slot { text_start: u32, text_len: u16, frequency: u32 }`。查出來的 `Match` 借用 arena 裡的 `&str`，不複製。

**結果**：RSS 480 MB → 148 MB。這個佈局也是後來二進位制化（`.qj` 容器）能直接 mmap 的前提：記憶體裡就是幾段連續陣列。

## 第二輪：查詞（2026-09-04）

**起因**：單字母 `k` 一鍵 30 ms，全簡拼 `zhgdoima` 70 ms，長全拼 20 ms。當時 `lookup_pattern` 是對整個索引線性掃、
逐鍵 split 音節比對。

**觀察**：鍵按位元組序排好，「以某段字首開頭的鍵」一定是連續區間。所以查詞可以逐音節位置二分收窄：

- 完整音節：區間裡直接二分到 `字首 + 音節 + 空格`（`kai ` ），一步到位。
- 簡拼位置（`k` 是字首）：區間裡出現的不同音節是一塊一塊的（`ka …`、`kai …`、`kan …`），每塊只看第一條鍵就能算出這塊的
  子區間，跳著掃，代價與實際出現的音節組合數成正比，與首音節下有多少鍵無關。
- 區間收到 48 條以內改成線性比對：小區間再二分加遞迴反而貴，全簡拼時小塊極多。
- `lookup_exact`（只要音節數正好等於模式長度的詞）與 `lookup_pattern`（≥）同一套收窄，只是最後一級不收更長的詞。
  整句轉換的詞圖格子和「輸入字首也出候選」都只要精確等長的詞，之前用 ≥ 版再過濾，白查一大片長詞。

**同一次查詢裡的重複**：不同切分共享很多字首（`zh g d o…` 的幾種切法前幾段一樣），同一個字首模式只查一遍（`HashMap` 記憶化，
鍵是模式串）。

**排序**：單字母簡拼命中兩萬條，`sort_by` 的比較器裡每次 `chars().count()` 讓排序佔幾十毫秒。改成排序鍵先算好再排
（`SortKey` 元組，文本借自詞庫），遠超上限時先按結構鍵 + 詞頻 `select_nth_unstable` 砍到 2 × 上限再算上下文得分、再排，
候選最多 500 條（同音字最多的音節也不到這個數，再往後沒人翻）。去重只做到夠數為止。

**結果**：長輸入 20 ms → 0.2 ms，`zhgdoima` 70 ms → 1–3 ms，單字母 30 ms → 3–4 ms。

## 第三輪：逐鍵（2026-09-05）

**起因**：簡拼整句、拼寫糾錯、英文模式幾個功能疊上去之後，想在給測試者打包前系統量一遍。先加了 `--typing` 逐鍵模式，
一跑就看到三個極端：`zhzhzhzhzhzhzhzh` 16 鍵 44 ms（parse 39 ms），`sssssssssssssss` 15 鍵 21 ms（rank 13 ms），
單字母首鍵 9–10 ms。常規輸入（`woxiangquchifan`、`kaifa`）都在 1–4 ms，問題全在簡拼極端情況和首鍵。

### parse 39 ms：糾錯變體

拼寫糾錯對「不像話」的拼音列舉一處編輯的全部變體（換位、替換、插入、刪除，16 字母約 1500 個），每個變體跑一次
完整切分 DP（`parser::segment`，帶 `Vec<Segmentation>` 克隆和排序）。任何非末尾有簡拼的輸入都算「不像話」，
所以全簡拼句子每鍵都在做這件事，而且長度越長變體越多、每個變體的 DP 也越貴，二次增長。

**改法**：加一個只回答是否、不分配的 `parser::is_fully_segmentable`（一維可達性 DP，每個位置查 trie 拿合法音節長度），
變體先過它，剩下的幾個才做真正的切分。**結果** 39 ms → 0.17 ms。

### rank 13 ms：整句詞圖的格子查詞（彎路在這裡）

`sss…` 15 個音節，詞圖有 15 × 8 = 92 個格子（最長詞 8 音節），每個格子對詞庫做一次 `lookup_exact`。

先後猜錯了兩次：

1. 猜是格子內的排序：比較器裡每次查兩張雜湊表（使用者選擇次數、個人出現次數）。改成得分先算好再排——沒變化（12.6 → 11.9 ms）。
2. 猜是路徑打分裡的 bigram 查詢：300 萬對 `(u64 鍵, 計數)` 扁平陣列二分，一次 22 步隨機訪問。改成按前詞分組的 CSR
   （`offsets[v]..offsets[v+1]` 是 v 的後繼段，段內按後詞編號二分），記憶體 48 MB → 24 MB——也沒變化（11.6 ms）。

然後才打點：92 個格子查詞共 25 000 條原始命中、10 ms；路徑打分只有 0.7 ms。**熱點是詞庫收窄本身**：
`s s s s` 這種簡拼格子要把詞庫裡所有 s 開頭音節的組合走一遍，每步一兩次二分，這是第二輪那個演算法的固有代價，
再怎麼調常數也省不掉。

**改法**：不省這一次，省後面十四次。敲鍵是增量的——第 n+1 鍵只新增以它結尾的最多 8 個格子，其餘格子上一鍵都算過。
加 `sentence::SpanCache`：鍵是格子模式（每個位置的寫法與是否完整，含模糊音寫法），值是排好、截好的候選（`Arc<[SpanWord]>`，
不再借用詞庫）。候選只與詞庫、使用者詞、選擇次數、個人出現次數有關，Engine 在 commit / `learner_mut` / 換 Learner 時整個清掉；
超過 8192 個格子也清。**結果** 12 ms → 1 ms，15 鍵平均 2.5 ms。

前兩次改動保留了：得分預算是對的寫法，CSR 是更好的佈局（也是二進位制化時的佈局），只是它們不是這個瓶頸。
教訓寫在最後。

### 首鍵 9 ms：單字母命中 78 000 條

`s` 一鍵：`lookup_pattern([s…])` 把所有首音節 s 開頭的詞全收進來（78 573 條），然後每條算一次使用者權重（雜湊查表）、
一次模糊音比對、構造 `Scored`，再進預選。打點分攤：查詞 1.9 ms、構造 3.0 ms、預選 + 排序 3.8 ms、插入 1.4 ms
（這 1.4 ms 是 `jiff` 首次載入時區，程序生命週期裡只有一次）。

改了四處，每處都是常數級：

- 詞頻、語言模型詞表、個人 n-gram 的 `HashMap` 換 `foldhash`（SipHash 一次幾十納秒，這裡一鍵要查幾萬次）。
- 預選鍵從 9 元組打包成一個 `u128`（精確、覆蓋字母數、簡拼數、末音節完整、選擇次數、詞頻、模糊、字數依次佔位），
  `select_nth` 比整數而不是逐項比元組；預選邊界上的平手不再拿文本決勝，誰留下無所謂，最終排序仍用完整鍵。
- 沒開模糊音時不逐條做模糊命中比對（`is_fuzzy_hit` 要 split 音節）。
- `scored.reserve(hits.len())`，省掉幾次翻倍搬家。

**結果** 首鍵 9–10 ms → 4.5–5.6 ms，模糊音全開 8 ms。

### 這一輪之後的數字

| 場景 | 改前最慢一鍵 | 改後 |
|---|---|---|
| 全拼長句 `woxiangquchifan` | 3.8 ms | 3.1 ms |
| 全簡拼 15 字母 | 10.8 ms | 3.4 ms |
| `zhzhzh…` 16 字母 | 44 ms | 8 ms |
| `sss…` 15 字母 | 21 ms | 4.5 ms |
| 單字母首鍵 | 9 ms | 5 ms（模糊音全開 8 ms） |
| 英文模式（2.1 萬詞表補全 + 一處編輯糾正） | 0.24 ms | 不變 |
| 啟動 | 1.03 s | 0.93 s |

啟動裡詞庫解析 0.24 s、語言模型表 0.62 s，這是 TSV 逐行 parse + 建雜湊表的成本，靠演算法省不掉，要改檔案格式（下一節）。

## 第四輪：啟動（2026-09-05，`.qj` 容器）

**起因**：啟動 0.93 s，詞庫 TSV 解析 0.24 s、語言模型兩張 TSV 解析 + 建雜湊表 0.62 s。這是 89 萬行 + 350 萬行的逐行 parse、
排序、`HashMap` 插入，演算法上沒得省，要改檔案格式。

**改法**：`crates/qingjian-format` 的 `.qj` 容器（設計見 [design/architecture.md](../design/architecture.md)）。要點是**記憶體佈局就是檔案佈局**：
第一輪的 arena + 偏移、第三輪的 CSR 本來就是幾段連續陣列，直接落盤；開啟時 mmap，只校驗頭、分節邊界、每條偏移是否越界。
語言模型的 `HashMap<String, (id, count)>` 換成檔案裡的開放定址雜湊索引（槽裡放編號、鍵留在 arena、FNV-1a + fmix64 穩定雜湊），
TSV 解析路徑也改成產出同樣的結構，查詢程式碼只有一份。

**彎路**：第一版 `Text::deref` 用帶校驗的 `from_utf8`，每次取 `&str` 都掃一遍 30 MB arena，CLI 直接卡死超時。
開啟時校驗一次、之後 unchecked 才是對的；unsafe 的前提（檔案只整體替換、從不就地修改）寫在註釋裡。

**結果**：

| | 改前 | 改後 |
|---|---|---|
| 詞庫載入 | 240 ms | 12 ms（其中大半是逐條校驗偏移） |
| 語言模型載入 | 620 ms | 9 ms |
| Engine 就緒 | 930 ms | 50 ms |
| 檔案體積 | dict.tsv 26 MB + lm TSV 48 MB | dict.qj 46 MB + lm.qj 46 MB |

體積反而大了：TSV 裡詞頻是十進位制文本，容器裡是定長 `u32`，加上雜湊表一半是空槽。以後要減體積就上變長編碼，
但那會破壞零複製，除非只對冷欄位（詞頻）做。首鍵從冷頁開始時多 2–3 ms（缺頁），`madvise(WILLNEED)` 已開，
再要就啟動時後臺執行緒摸一遍頁。

## 第五輪：釋義表進容器（2026-09-05）

**起因**：釋義表全量生成後從 6 萬詞漲到 24 萬詞，TSV 解析從 20 ms 漲到 90 ms，啟動 170 ms。

**改法**：`Glossary` 改成雙存法：TSV 解析出來還是雜湊表；`.qj` 是字串 arena + 詞條表（詞的偏移、釋義段）+ 釋義表
（譯文 / 讀音 / 詞性縮寫各一段偏移）+ 檔案裡的雜湊索引，與詞庫、語言模型同一套 `qingjian-format`。查表時按需拼出 `Translation`，
每鍵幾百次、每次幾十納秒的雜湊加幾次切片。**結果** 釋義表載入 90 ms → 8 ms，啟動 170 ms → 47 ms（冷啟動 116 ms，缺頁）。

## 第六輪：詞圖敲錯邊（2026-09-06）

**起因**：整句詞圖每個完整音節多了十幾種敲錯寫法（`correction::typo`），格子查詞的分支隨之變多。

**數字**（release，帶使用者資料，`--typing`）：28 鍵句子最慢 3.5 ms → 4.2 ms、平均 0.46 → 0.64 ms；40 鍵句子最慢 2.9 → 4.7 ms、平均 0.66 → 0.95 ms。
仍在每鍵 10 ms 的目標內。已做的收斂：換鍵只算相鄰鍵（變體數少一半以上）；詞級候選不加敲錯邊；整段一處編輯的變體上不再疊敲錯邊
（`nihoama` 的 parse 從 12 ms 回到 1 ms）；非末尾帶簡拼的切分、雙拼、不到 4 個字母的不加。格子快取的鍵含全部寫法，敲錯邊不影響增量複用。
**沒做的**：格子裡敲錯變體的命中先算全部再按 e^(−代價) 打折截斷，理論上可以按代價分層、原樣夠多就不查變體，等數字需要再說。

## 第七輪：句末英文詞（2026-09-08）

**改動**：`Engine::split_english_tail` 每次查詢多做一遍「尾段是不是英文詞」的掃描：從最長到最短試每個字尾查英文詞表（雜湊表），
命中且整段能讀成拼音時再多跑兩次整句轉換比分（頭段一次、整段末尾單字母也讀一次），都走 `SpanCache`。
**數字**：`--typing woxiangxuehaorust` 每鍵最慢 5.0 ms（改前 4.65 ms），平均 0.8 ms；回放 4867 條與改前完全一致。
比分只在尾段真是詞表裡的詞時才發生，平時的鍵只多幾十次雜湊查表。

**神經重打分**的延遲另見 `docs/notes/neural-rescoring.md`：
M1 上 Metal 空前文單條 6 ms、64 字前文 × 8 條 133 ms，離每鍵預算差一個量級，要做前文 KV 快取與非同步防抖。

## 第八輪：本地整句模型（2026-09-08）

**起因**：字級 Transformer 重打分在整句評測集上過了門檻（+4.3 個點，見 `neural-rescoring.md`），但同步打分一次查詢 60 到 70 ms、20 字長句 800 ms，
遠超每鍵 10 ms 預算，不能放進按鍵回撥。

**定位**：`cargo test --release -p qingjian-neural --features metal -- --ignored --nocapture` 的延遲探針（M1，small 23M，8 條約 8 字的候選）：

| 後端 | 空前文 1 條 | 空前文 8 條 | 64 字前文 1 條 | 64 字前文 8 條 |
|---|---|---|---|---|
| Metal，無快取（改前） | 6 ms | — | — | 133 ms |
| Metal，前文 KV 快取 | 6 ms | 20 ms | 8 ms | 28 ms |
| CPU（candle gemm），前文 KV 快取 | 17 ms | 61 ms | 19 ms | 73 ms |

前文重算與快取命中只差 1 到 2 ms：前文那 64 個 token 一次前向很便宜，貴的是每條候選一遍、每層十幾個小運算元的排程；
所以候選越多越慢，與候選長度關係不大，也是 CPU 反而更慢的原因（同樣多次小運算元）。Accelerate 後端在本機編不過，沒量。

**改法**：
1. `qingjian-neural::PrefixCache`：前文（去掉最後一個 token）每層的 K / V 算一次存下來，候選只算「前文最後一個 token + 候選」；結果與 Python 打分對拍不變。
2. Core `engine/rescoring`：一次查詢裡整句轉換跑好幾遍（糾錯變體、中英混輸比分），所有路徑文本進一張「前文 + 文本 → 神經分」快取，
   同步打分器只補缺的分：評測每句 69 → 27 ms（`--eval-text` 300 句，λ 0.25 前文 64）。
3. 非同步：打分在後臺執行緒，按鍵回撥只跑詞級模型；殼停鍵 80 ms 後把缺分的文本一批送去，20 ms 輪詢，到了重查一次只重畫當前頁。
   `--neural-async` 走同一條路，300 句上與同步逐句一致，每句 35 ms（含等待與兩次查詢）。

**結果**：按鍵路徑回到改前（查詢 0.7 ms），模型的意見在停鍵後約 100 到 130 ms 到（80 ms 防抖 + 一批 20 到 30 ms + 輪詢間隔）。
模型後臺載入 + 預熱：程序冷啟動 353 ms（fp16 56 MB mmap）；機器第一次編譯 Metal 核心那次 12 秒，系統快取後不再有。
記憶體：權重按 f32 上 GPU 時輸入法程序 273 MB（其中 GPU 側 172 MB）；改成 Metal 上預設 f16 後 CLI 評測程序 240 → 131 MB（GPU 側 185 → 60 MB），
300 句評測結果與 f32 逐句一致、與 Python 對拍仍在容差內，延遲略快（64 字前文 × 8 條 27 → 25 ms）。空閒時 CPU 0 到 1%，敲鍵那一刻 10 到 18%。
評測集全量（8322 句，`--eval-text`，同步模式，λ 0.5 前文 64）：改前平均 61 ms、最慢 781 ms；改後平均 24 ms、最慢 101 ms，命中率不變（41.6% / 79.1%）。

## 經驗

1. **先量再改，先打點再改。** 第三輪猜錯兩次的原因是憑「常識」判斷熱點（雜湊查表、大陣列二分都是教科書裡的慢點），
   而真正的熱點是自己兩天前寫的、以為已經快了的收窄演算法。兩個改動花的時間比打點多得多。
2. **量真實的工作負載。** 輸入法的真實負載是逐鍵增量查詢，不是「查一次整段」。`--typing` 一加，之前一直測不出的問題
   立刻出來。同理，測極端輸入（全簡拼、重複字母、模糊音全開）而不只測順手的例子。
3. **增量場景優先想快取，而不是最佳化單次。** 格子查詞的單次代價是演算法固有的，但相鄰兩鍵 90% 的工作是重複的。
   快取的難點是失效條件，要把「結果依賴什麼」列清楚（這裡是詞庫、使用者詞、選擇次數、個人計數），在改這些東西的每個入口清快取。
4. **常數最佳化要成批做並分別量。** 雜湊器、鍵打包、跳過比對、預留容量，單看每項 0.5–1.5 ms，合起來首鍵砍掉一半。
   但它們排在演算法和快取之後，先做演算法。
5. **資料佈局服務兩件事：查詢速度和檔案格式。** arena + 偏移、CSR 這些選擇讓記憶體結構可以直接落盤，二進位制化（第四輪）只花了半天，
   而且解析路徑和對映路徑共用同一套查詢程式碼。
6. **效能改動要有對拍或迴歸。** 收窄演算法與線性掃描隨機對拍；排序 / 快取改動跑全部單元測試加固定輸入組。
   沒有這層保護，`select_nth` 換排序方向這種改動很容易悄悄改掉候選順序。
